# Product Context

## 目标用户

- 需要把海外 X 内容转化为中文内容的创作者。
- 关注 AI 工具、开发者效率、Agent 与 Coding 工作流的人群。
- 希望使用免费或低成本模型完成内容生产的个人用户。

## 核心用户流程

1. 在 `01 粘贴 X 内容` 输入完整帖子或单条帖子 URL。
2. 按需调整目标读者、语气、深度等创作偏好。
3. 点击“生成小红书长文”。
4. 服务端解析 URL（如有），把清洗后的偏好和原文注入 Markdown 提示词。
5. 按 Gemini → Groq Qwen → 智谱 GLM → 硅基流动 Qwen →
   OpenRouter Free 顺序调用模型。
6. `02 小红书长文` 按 7 步发布流程展示可复制内容。
7. `02` 在对应发布步骤内显示自动检查结果与失败原因。
8. 如果自动检查失败，用户可在对应部分执行修复；完成后重新检查整稿。
9. 用户人工确认内容质量，最后在小红书完成排版和发布。

首次生成成功后服务端自动创建历史记录；修复成功后追加版本。用户可以通过
右上角“查看历史”查看、载入或删除记录，载入本身不调用模型。

## 小红书 7 步发布流程

| 步骤 | 产品行为 |
|---|---|
| 01 输入长文标题 | 生成 3 个通过硬规则的候选，选择后写回 Markdown 第一行；支持重新生成 |
| 02 输入长文正文 | 可生成并确认新正文版本；复制或导出仅含正文的 Markdown 文件 |
| 03 点击一键排版 | 用户在小红书操作，生成封面与内容卡片 |
| 04 修改发布标题 | 独立生成 3 个不超过 20 字的候选，选择或重新生成 |
| 05 输入正文描述 | 使用当前正文摘要，支持重新生成并确认新版本 |
| 06 输入标签 | 复制同一行的 8 个 `#标签`，支持重新生成并说明数据模式 |
| 07 检查并发布 | 汇总依赖状态；正文变化后提示 04–06 基于旧正文 |

## 内容合同摘要

完整规则以 [`Long-form-post-prompt.md`](../Long-form-post-prompt.md) 为准。

- 标题：18–20 字，恰好 2 个 Emoji；默认使用“超全干货”，仅正文
  8000 字以上可以使用“万字深度”。
- 正文：不设最低字数，按原文信息量自然展开；最大 10000 字。
- 开头：建议 150–450 字，短主题可以更精简。
- 实战落地：按主题适用性展开，不设最低字数，不得为凑篇幅虚构内容。
- 摘要：220–280 字，同时不超过发布页 1000 字限制。
- 主体：按内容需要设置 2–15 个连续编号大章节；每章 1–3 个小节点。
- 卡片切分：由小红书“一键排版”自行完成；正文禁止使用 `---`、
  “未完待续”等伪分页信号。
- 标签：恰好 8 个唯一标签，同一行，每个以 `#` 开头。
- 固定尾部顺序：
  1. `## 正文小结 / 摘要`
  2. `## 推荐标签`
  3. `## 【审稿自查】`
- 审稿自查：3–5 条风险或优化建议。
- 正文内部保留`#`、`##`、`-`和`1.`表达标题与列表语义；不使用
  加粗、引用、表格或代码围栏。
- 复制正文时优先写入`text/html`富文本，同时提供去除井号、把`-`
  转为`•`的`text/plain`兜底，避免平台不解析 Markdown 时显示标记。

## 内联规范检查的信息架构

- `02` 顶部显示整稿自动检查汇总，不单独设置检查工作区。
- 长文标题检查放在步骤 01；步骤 04 使用独立发布标题字段和 20 字上限，
  不再复用步骤 01 的值或校验状态。
- 正文、摘要、标签检查分别放在步骤 02、05、06。
- 固定分区、审稿自查和人工复核放在步骤 07。
- 未通过项默认展开；通过项默认折叠。

### 自动检查：11 项

- 标题：字数。
- 正文内容：总字数、开头、主体结构、实战落地。
- 正文小结 / 摘要：摘要字数、发布描述。
- 推荐标签：标签数量、标签格式。
- 输出结构：分区与顺序。
- 审稿自查：风险点数量。

### 人工内容复核：8 项

- 二度创作。
- 案例与洞见。
- 语气与表达。
- 实战完整性。
- 结尾互动。
- 排版可读性。
- 摘要与标签质量。
- 审稿建议质量。

人工项只提示“发布前确认”，不参与自动失败计数和自动重写。

## 关键 UX 约束

- 两个主面板保持同一高度。
- 整页不产生滚动条；各面板内部独立滚动。
- 移动端仍保持两段固定高度，而不是把整个页面纵向撑开。
- 输入说明放在文本框 placeholder，不额外占用正文空间。
- 生成后不能要求用户一次复制整个 Markdown。
- `02` 展示唯一的结构化正文源稿；富文本和纯文本兜底必须由该字段
  确定性派生，不得维护两份独立正文。
- `02` 的 Markdown 导出与复制共用同一正文数据源；文件只用于小红书
  标题与正文编辑页的“从文件导入”，并提示导入会覆盖已有正文。
- 01、02、04、05、06 的复制操作统一位于内容预览顶部；第 02 步的复制
  与 Markdown 导出并列，不得以操作列压缩正文预览宽度。
- 标题和标签使用紧凑预览，正文描述使用中等预览，长文正文使用较高的
  内部滚动预览并支持展开或收起；不得因此破坏整页无滚动约束。
- 复制和 Markdown 导出使用具名图标按钮；视觉上不显示操作文字，但必须
  保留`aria-label`、原生悬停提示和至少 44px 的移动端点击区域。
- 局部重新生成产生候选，不得自动覆盖当前内容；正文候选被采用后，
  04、05、06 分别标记为基于旧正文，直到用户重新生成或选择新候选。
- 没有可信趋势数据时，标签只能标记为“基于正文生成”，不得使用
  “实时热门”或“当前趋势”等文案。
- `02` 同时承载对应部分的检查、修复入口和发布前人工复核。
- API 配置入口固定在页面右上角。
- 页面右上角“设置”是唯一配置入口，01 输入区不重复显示偏好或入口。
- 创作偏好使用白名单结构化选项和有限自由文本，保存在浏览器本地。
- 固定输出协议、事实边界和平台硬约束不向用户开放编辑。
- “查看历史”与“设置”并列放在右上角，不占用 01/02 工作区高度。
- 历史默认按最近更新时间倒序；一次首次生成是一条记录，修复是同记录版本。
- 载入历史后重新运行前端检查，恢复原始输入与对应创作偏好，但不调用模型。
- 删除需要在历史弹窗内二次确认。
